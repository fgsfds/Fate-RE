---
name: fate-exact-restoration
description: Restore Fate-RE assembly routines to C with the pinned Watcom 10.5 compiler, verify code and LE relocations, rebuild the exact DOS executable, and update coverage.
---

For parallel work, also load `fate-restoration-coordination`; for new compiler/ABI
hypotheses, load `fate-compiler-research`. The configured cost-tiered project agents and
their ownership/handoff rules are documented in `docs/RESTORATION-AGENTS.md`.
Adding or loading these profiles does not resume paused restoration.

1. Check the branch and working tree. Run `python tools/restore.py context <routine>` for bounded routine-specific metadata, source locations, neighbors, fixtures, and failed attempts. Follow only the relevant references; do not read complete registries or inventories. See `docs/RESTORATION-WORKFLOW.md` as needed.
2. Probe in an ignored scratch directory with `python tools/restore.py probe <routine> --build work/<batch> --reference <verified.exe>`. Compiler options live in `tools/data/restoration-units.txt`; compilation stays pinned and windowless. `probe` and `validate --changed` perform focused span/LE verification; add `--fixtures` only when wanted (some fixtures require a complete baseline). For actor movement or tile copying, use `restore.py behavior <routine>` to diagnose nonmatching candidates before exact checks; saved failing cases can be replayed with `--case-file`. Behavioral success never qualifies exact coverage. Consult `docs/WATCOM-IDIOMS.md` and the cached `check_watcom_idioms.py` probes before repeating compiler experiments. Use `validate --changed` against an existing provenance baseline for the fast edit loop. Full diagnostics stay in files; inspect the bounded first byte/instruction or relocation mismatch before widening output. Prefer ordinary C for the full routine. Try register-only ABI declarations and compiler-recognized idioms before adding hand-written inline instructions. Treat existing inline instructions as candidates for further restoration.
3. Use `bind_leaf_details` and `verify_leaf_relocations` from `tools/verify_c_leaf.py` against a verified reference executable. Compare both machine code and LE sites and targets. Keep a short attempts entry only when an unresolved mismatch informs the next probe. Record the flags, first meaningful mismatch, and next hypothesis. Remove resolved entries when the exact replacement ships. Preserve the exact assembly until its replacement qualifies.
4. Integrate an exact object in `tools/data/restoration-units.txt`, `verify_c_leaf.py`, and `verify_c_suite.py`. Remove the matching entries from `verify_assembly_suite.py` and preserve padding and reachable interior labels. For a compiler-generated switch table, reuse bind_switch_group and register the binder once in `restoration_registry.py` so verification and linking handle the CODE fixups. Register focused fixtures and their affected objects in `tools/data/restoration-fixtures.txt` when behavior or ABI coverage is missing. When C/assembly registrations change, refresh inventories with step 6 before step 5: the linker reads those inventories, and the refresh verifies the proposed spans and whole image atomically. Source-only edits keep the normal step 5 path.
5. From the repository root, run the exact whole-executable acceptance gate:

   ```powershell
   python tools/restore.py validate --build work/restoration-build
   # Optional independently verified reference, distinct from the output:
   python tools/restore.py validate --build work/restoration-build --reference <verified-original.exe>
   ```

   Default validation (`--exact` is an alias) builds current C/NASM with content-checked caches, pins inputs, checks compiler freshness and snapshot stability, and links production `FATE.EXE`. The packer checks its pinned whole-file hash, including relocations. An optional reference is hash-checked before building, must differ from the output path, and is compared directly to the result. Merely hashing a stale executable is insufficient. Exact acceptance does not run all unit tests, the idiom suite, per-span inventory reports, coverage-docs, behavioral fixtures, emulator dependencies, or game smoke. Use `validate --full` for tooling changes or periodic broad regression checkpoints: it adds unit tests, idioms, per-span inventory/coverage checks, and fixtures, but not game smoke. `--smoke` is allowed only with explicit `--full`; skip game smoke for the current task. Exact or full `--clean --build work/<new-name>` requires a new directory and uses no compiler/NASM caches. `doctor --build work/restoration-build` accepts current exact or full reports and verifies artifact hashes. For direct fixtures and unittest discovery, put `tools` and the verified dependency-cache directory on `PYTHONPATH`.
6. Run `python tools/refresh_code_inventory.py <build> <verified-reference.exe>` when registrations, inventories, or coverage change, not after every source-only edit. It checks the pinned reference, compiler freshness, and whole linked image, then generates inventories and the coverage overview in `docs/RECONSTRUCTION.md`; `python tools/restoration_coverage.py --check` detects drift. Attribution and marker audits remain separate and are required to report C/assembly percentages honestly, especially when inline attribution changes. Report changed routines, bytes and LE sites, whole-image verification, and percentages for standalone assembly spans and measured inline assembly. Keep mixed C objects separate from assembly-free C in coverage claims. OMF timestamps can change object hashes between clean builds. Compare linked code and fixups before investigating an object hash difference.
